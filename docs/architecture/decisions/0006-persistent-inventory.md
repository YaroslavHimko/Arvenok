# ADR 0006: Persistent character backpack

- Status: accepted for inventory v0.1
- Date: 2026-11-19

The project already had an authoritative single-writer world, stable character GUIDs, private progression RPCs and an interface-backed atomic JSON character repository. No inventory/equipment model existed. Extend these boundaries without adding a project, service, scene root or dependency edge.

Contracts defines catalog read models, immutable stacks, occupied slot records, inventory requests, snapshots and save state. Simulation embeds `content/items/catalog-v1.json`, validates definitions, and prepares complete inventory mutations. Every stack has a server-generated GUID and opaque, ordered key/value instance metadata; all metadata affects compatibility. Equipment and recipes have maximum stack size one. Item IDs are stable catalog keys. Capacity is configured in the catalog and saved per character; the default is 24 and the current validation ceiling is 48. No expansion mechanics exist.

`InventoryRules.Prepare` never mutates its input. Client moves/swaps/merges/splits/sorts validate slot IDs and revision. Trusted `InventoryExchange` removes multiple compatible ingredient types and then inserts outputs into a copy, accounting for newly freed slots. Any error returns the original state and no receipt. Successful preparation returns a complete new state. This enables future coordinators to prepare multiple inventories or world-loot ownership together before committing. There is no loot, gathering, crafting, recipe knowledge, equipment transfer or trading implementation in this milestone. A future multi-owner transaction must persist all affected ownership together; the current per-character file store does not claim cross-character atomic commits.

Each request has a GUID and expected inventory revision. Client and trusted-server receipt namespaces are separate, so a client-chosen ID cannot reserve or poison a reward ID. Successful client receipts retain the last 128 results; unchanged older requests remain harmless because their precondition is stale. Reusing a retained ID with different arguments is rejected. Trusted reward/removal receipts are retained permanently in the character file, up to a development limit of 4096. The limit rejects additional trusted exchanges explicitly instead of evicting receipts and allowing duplicate grants; move/sort/split operations remain available. A production reward journal should replace this storage limit before automatic item-producing gameplay ships. Retries must repeat the same request, including its expected revision.

World inventory submission derives ownership exclusively from the transport peer. Clients never send a character ID or receive arbitrary item-creation/removal RPCs. Rate limiting is separate from combat input. Full private snapshots go only to the owner. Inventory RPC success is acknowledged after the existing serialized save queue commits the complete character aggregate, including progression and inventory together. Client retries reuse the original request every three seconds while pending; there is no optimistic ownership model. Concurrent requests with the same prior revision cannot both commit. Server-internal exchanges also publish private changes after saving.

Save schema 2 adds inventory to `CharacterRecord`. Schema 1 progression saves migrate once to an empty configured backpack, preserving character identity and progression and advancing the save revision. Schema 2 missing/invalid inventory is corruption, not an invitation to reset items. Load validates catalog references, ordered unique slots, quantities, metadata, identities and receipts. Repository writes reject older aggregate or inventory revisions and conflicting equal revisions. Atomic rename commits one complete character file; the existing directory lease excludes other processes, and a repository lock protects read/check/write against concurrent threads. Migration also uses atomic replace. Explicit failures never overwrite corrupt saves with an empty character.

The only development grant is offline `--server --grant-inventory <character-guid>`, available in Debug builds, with no client RPC. It requires the normal exclusive save-directory lease, grants a fixed kit through the same insertion rules, persists a fixed per-character operation ID, and exits. Login/reconnect never grants items. Release builds reject the command.

`InventoryHud` and `InventorySlotControl` are reusable native Controls. I opens Backpack, K opens Skills, and each closes the other. The capacity-driven six-column grid scrolls for larger saved capacities. Drag/drop uses Godot's Control protocol and revision/stack preconditions; Shift-drag or Split opens an inline quantity chooser. All quantities and tooltips render confirmed server snapshots. Small authored SVG placeholder icons can be replaced using catalog icon keys; no external art license is asserted.
