# ADR 0007: Monster loot, two equipment slots and direct-use crafting

- Status: accepted for v0.1
- Date: 2026-11-20

Extend the existing character aggregate, inventory rules, monster contribution ledger and Godot session. No new project, dependency edge, scene root, service or combat implementation is introduced. The supplied handoff is design input; its source JSON is retained under `content/art-source/ui/arvenok-loot-v1/data`. Runtime item definitions extend `content/items/catalog-v1.json`, retaining all ten legacy IDs. `EconomyCatalog` embeds and validates the six recipes, four monster tables and timing/range rules. Artwork remains presentation-only.

Schema 3 adds `EquipmentState` with exactly Weapon and Body fields. Instances move between backpack and equipment without cloning. Inventory revision covers both ownership locations; character revision also advances. Schema 1 migrates directly to an empty backpack and equipment, schema 2 retains its complete backpack and adds empty equipment. Both preserve progression and advance the aggregate revision once. Unknown IDs, missing schema-3 state, invalid gear restrictions and duplicate identities produce diagnostics and leave the original file intact. Legacy training equipment and its recipe remain stored but are not silently remapped to functional equipment.

The world derives identity from its peer mapping. Equipment requests name an owned instance and expected inventory revision. Class/level restrictions apply only to equipping. Swaps use the vacated source backpack slot; unequip requires an empty slot. Five seconds must have elapsed since damage, with no cast, attack intent, recovery or dash in progress. Effective damage is ranked ability damage plus weapon damage once before existing reduction. Effective maximum HP is base class HP plus body HP. Equipping preserves current HP, unequipping clamps it, and reconnect/respawn use the recomputed maximum. Icons do not replace animated character appearance.

Loot uses the existing effective-damage eligibility window, contribution threshold, alive/range checks and disconnect handling. Highest credited damage wins; a tie uses stable character GUID order. Loot and EXP remain separate outcomes. A bounded per-monster life number guards rolling once per death, including after respawn. Independent probabilities and weighted groups use server RNG. Each successful roll creates a transient token with unique drop/item/death IDs, owner, valid swept corpse-relative position and server timestamps. Protection lasts 20 seconds, public access another 100; expiry or restart removes uncollected tokens. Replicated full snapshots include tokens and reconcile their removals. Pickup requires a living player, rights, range of 64 pixels and an unobstructed traversable segment.

Crafting consumes the selected scroll identity and all ingredients across backpack stacks, then inserts exactly one server-defined output with a new GUID and `crafted_recipe` provenance. Preparation copies ownership, so missing ingredients or invalid requests change nothing. There is no class/level gate on crafting. The consumed stack-one scroll always frees a slot for these one-output recipes, including a previously full backpack. The generic inventory exchange capacity checks remain available for later recipes with more outputs.

Equipment, crafting and pickup share the existing client receipt namespace, with a distinct economy fingerprint domain and a stored result instance ID. The most recent 128 successful client operations survive restart. An older exact replay has a stale revision; consumed scrolls and removed drop IDs provide additional one-use guards. Trusted internal reward receipts keep their existing separate namespace. Reusing an ID with different content rejects. Failed requests record no ownership mutation; a retry may succeed after the unmet condition changes.

For the development JSON backend, economy RPCs drain the asynchronous character save queue, then prepare, synchronously save the complete aggregate, and commit in-memory ownership without an intervening await. One in-flight economy request per peer and the world's single writer serialize competing claims. A failed save leaves both character and ground token unchanged. Success is acknowledged only after the durable atomic file replacement. If the process exits after saving but before removing a token or replying, reconnect restores the receipt and restart clears transient ground loot; it cannot grant the drop twice. This narrow synchronous save is a deliberate development exception to off-thread persistence, and may briefly stall the world. Production storage should replace it with an asynchronous transactional claim coordinator. Cross-character trading and durable world-loot storage are not implemented.

The native backpack adds an equipment panel, comparison tooltips, compatible equipment drag targets, direct-use recipe preview and crafting feedback. I/E open the same window; K remains Skills; F requests nearby loot. Presentation only submits intent and displays server-confirmed state. `tools/smoke-economy.ps1` uses isolated server files and real ENet clients; its offline fixture items are not login grants or client RPC capabilities.
